# Q
What is the minimal SQLite + Ascent (Crepe) rule set that binds CVIR promotion receipts (candidate, method_hash, tick, stage, verdict, evidence_hash, signature) to a fail-closed Rust admission gate, such that stale/future/contradictory receipts are rejected deterministically, and which replay test (permutation invariance over 1000 seeded runs) proves the gate's decisions are bitwise-identical across restarts?

# A
CVIR: SQLite + Ascent + fail-closed Rust gate

Basis: Ascent (Sahebolamri et al., 2022; maintained through 2026), Crepe (Rust Datalog), SQLite transactional isolation. The following is a proposed implementation, not a published, experimentally verified CVIR system.

1. Minimal SQLite schema
SQL

CREATE TABLE receipts (
  id BLOB PRIMARY KEY,
  candidate TEXT NOT NULL,
  method_hash BLOB NOT NULL CHECK(length(method_hash)=32),
  tick INTEGER NOT NULL CHECK(tick>=0),
  stage INTEGER NOT NULL CHECK(stage BETWEEN 0 AND 7),
  verdict TEXT NOT NULL
    CHECK(verdict IN ('PASS','FAIL','REVOKE')),
  evidence_hash BLOB NOT NULL CHECK(length(evidence_hash)=32),
  signature BLOB NOT NULL,
  signer_id TEXT NOT NULL
);

CREATE TABLE admissions (
  candidate TEXT NOT NULL,
  method_hash BLOB NOT NULL,
  tick INTEGER NOT NULL,
  stage INTEGER NOT NULL,
  receipt_set_hash BLOB NOT NULL,
  decision_hash BLOB NOT NULL,
  PRIMARY KEY(candidate,method_hash,tick,stage)
);


Receipt signatures must cover every field, including domain/version, candidate, method, tick, stage, verdict and evidence hash.

2. Minimal Datalog policy

Executable logic shown in Soufflé-style notation; translate into Ascent macros with stratified negation.

prolog

// E(c,m,t,s): authenticated PASS
// X(c,m,t,s): authenticated FAIL/REVOKE
// P(c,m,t,s): admission request
// Complete snapshot and freshness checked in Rust.

ok(c,m,t,0) :-
    E(c,m,t,0),
    !X(c,m,t,0).

ok(c,m,t,s) :-
    E(c,m,t,s),
    s > 0, s <= 7,
    ok(c,m,t,s-1),
    !X(c,m,t,s).

blocked(c,m,t,s) :-
    P(c,m,t,s),
    !ok(c,m,t,s).


Stage mapping: MEASURE=0, FALSIFY=1, MATCHED_ABLATION=2, VERIFIED_OUTCOME=3, CAUSAL_CREDIT=4, BOUNDED_ADMISSION=5, REENTRY_TEST=6, CONTROL_INFLUENCE=7.

Scope: This minimal policy requires all evidence at the same logical tick. Multi-tick evidence needs a separately specified predecessor relation and explicit freshness semantics.

3. Fail-closed Rust admission gate

Within BEGIN IMMEDIATE:

Freeze logical tick T, policy version, trusted signers and candidate/method scope.

Verify signatures, evidence hashes and receipt completeness.

Reject future receipts (tick > T) and stale receipts (tick < T - TTL).

Reject contradictory verdicts for identical (candidate, method_hash, tick, stage); duplicates are deduplicated only when canonical payloads match.

Evaluate Datalog against the complete, validated snapshot.

Admit only if ok(candidate,method,T,requested_stage) and no conflicting evidence exists.

Store canonical receipt-set hash and decision hash atomically; otherwise rollback and return BLOCKED.

Invariant:

ADMIT ⇒ AUTHENTIC ∧ FRESH ∧ CONSISTENT ∧ COMPLETE_CHAIN

4. Deterministic replay test

cvir_replay_permutation_invariance_1000

Generate a fixed corpus containing valid, stale, future, duplicate, contradictory and revoked receipts.

For seeds 0..999:

Shuffle receipt insertion order into a fresh SQLite database.

Fix T, TTL, policy version and trust roots.

Evaluate requests in canonical order.

Serialize decisions using fixed field ordering and byte encoding.

Compare SHA256(canonical_decisions || canonical_admissions) against the reference run.

Restart Rust, reopen SQLite, repeat and compare.

Required assertion: All 1,000 runs produce bitwise-identical decision bytes and admission-state bytes. No invalid receipt causes admission.

Important: This is a specified test, not a reported passing result. Even if successful, it demonstrates determinism for the generated corpus, not mathematical proof over every possible receipt sequence.
