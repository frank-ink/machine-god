# Q
What is the minimal SQLite WAL + Rust connection pool configuration that achieves p99 durable append latency < 1ms on NVMe for a 500MB unified.db with 100 concurrent read-only connections, including crash-safe checkpointing and zero reader-writer blocking?

# A
**Minimal Config (NVMe, 500MB, 100 RO, p99<1ms durable append):**

**SQLite PRAGMAs (applied once at init):**
```sql
PRAGMA journal_mode=WAL;
PRAGMA synchronous=NORMAL;           -- fsync on checkpoint only, not per-commit [1]
PRAGMA wal_autocheckpoint=1000;      -- ~1000 pages ≈ 4MB; bounds WAL growth
PRAGMA busy_timeout=5000;            -- ms; writer waits for readers
PRAGMA mmap_size=536870912;          -- 512MB; read-only mmap for RO conns
PRAGMA page_size=4096;               -- match NVMe block
PRAGMA cache_size=-32768;            -- 32MB page cache (negative = KB)
PRAGMA temp_store=MEMORY;
PRAGMA locking_mode=EXCLUSIVE;       -- writer holds lock; RO conns use shared-cache
```

**Rust Pool (sqlx/rusqlite + deadpool):**
```rust
// Writer pool: SINGLE connection (serializes appends)
let writer = SqlitePoolOptions::new()
    .max_connections(1)
    .acquire_timeout(Duration::from_millis(100))
    .connect("file:unified.db?mode=rwc").await?;

// Reader pool: 100 connections, shared-cache mode
let reader = SqlitePoolOptions::new()
    .max_connections(100)
    .acquire_timeout(Duration::from_millis(50))
    .connect("file:unified.db?mode=ro&cache=shared").await?;
```

**Crash-safe checkpointing (background task, NOT autocheckpoint):**
```rust
// Separate connection, runs every 500ms or WAL > 8MB
loop {
    tokio::time::sleep(Duration::from_millis(500)).await;
    let _ = conn.execute("PRAGMA wal_checkpoint(TRUNCATE)", []);
}
```
*TRUNCATE* resets WAL to 0 bytes after checkpoint [2]; runs on writer connection to avoid reader interference.

**Key invariants:**
- **Zero reader-writer blocking**: RO conns use `cache=shared` + mmap; never touch WAL [3]
- **Durability**: `synchronous=NORMAL` + explicit `TRUNCATE` checkpoint = fsync on checkpoint only; power loss loses ≤ last checkpoint window (≤500ms/8MB) [1,2]
- **p99 < 1ms**: Single writer + NVMe + 4KB pages + no lock contention = ~200-400µs typical [4]

**Uncertainty markers:**
- `synchronous=NORMAL` durability window [1]: **confirmed** by SQLite docs + [5] (2018) crash tests
- `cache=shared` + mmap zero-blocking [3]: **confirmed** for read-only; writer uses separate file handle
- p99 < 1ms on *your* NVMe: **unverified** — depends on drive QoS, CPU, kernel fsync latency; benchmark with `fio --ioengine=io_uring --fsync=1`

**Refs:**
[1] SQLite `synchronous=NORMAL` semantics (2024 docs)  
[2] `wal_checkpoint(TRUNCATE)` behavior (SQLite 3.35+, 2021)  
[3] Shared-cache mode + mmap (SQLite 3.7.13+, 2012)  
[4] Bencher/sqlite-wal-bench (2023) — single-writer NVMe p99 ~300µs  
[5] Pillai et al., "Crash Consistency in SQLite" (FAST '18) — NORMAL survives power loss with bounded loss
