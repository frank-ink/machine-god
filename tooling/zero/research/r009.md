# Q
How can a fail-closed Rust admission gate over SQLite receipt tables (candidate, method_hash, tick, stage, verdict, evidence_hash, signature) be made bitwise-deterministic under permutation of insertion order, and which canonicalization (field order, integer encoding, hash chaining) is sufficient to guarantee identical decision hashes across 1000 seeded shuffles and process restarts?

# A
Bitwise-deterministic CVIR admission gate (Rust + SQLite)

Core principle: Determinism requires a canonical evidence set, deterministic policy evaluation, explicit serialization, and atomic state transitions. SQLite insertion order, row IDs, timestamps, and unordered Rust collections must never influence decisions.

1. Canonical receipt representation

Use a versioned binary format, independent of SQLite storage layout.

Field

	

Canonical encoding




domain

	

Length-prefixed ASCII CVIR-RECEIPT-V1

UTF-8, normalized or explicitly byte-exact, u32 length prefix

Exactly 32 bytes

Unsigned u64, big-endian

Unsigned u8, values 0–7

Unsigned u8: PASS=1, FAIL=2, REVOKE=3

Length-prefixed canonical UTF-8

Length-prefixed bytes

All integers use fixed-width encoding except explicit length prefixes. Reject invalid encodings, unknown fields, unsupported versions, and integer overflow.

Signature verification: Sign the canonical payload excluding signature; verify against pinned trust roots.

Receipt identity:

receipt_id = SHA256("CVIR-RID-V1" || canonical_signed_payload || signature)

Cryptographic canonicalization is an engineering specification; neither Serde nor SQLite automatically provides it.

2. Canonical evidence-set hash

Decode and validate every receipt.

Deduplicate byte-identical receipts.

Reject conflicting receipts for the same (candidate, method_hash, tick, stage) unless explicitly allowed by the policy.

Sort by canonical receipt bytes, using lexicographic unsigned-byte ordering.

Hash a length-delimited sequence:

H0 = SHA256("CVIR-SET-V1" || u64be(receipt_count))

Hi = SHA256("CVIR-LINK-V1" || H(i−1) || u32be(length(Ri)) || Ri)

The resulting Hn commits to the exact validated set independently of insertion order.

3. Fail-closed admission algorithm

Within BEGIN IMMEDIATE:

Freeze logical_tick, TTL, policy version, trust roots and requested stage.

Reject stale (tick < T−TTL), future (tick > T), invalid-signature and contradictory receipts.

Evaluate the complete eight-stage CVIR prerequisite chain.

Use deterministic BTreeMap/BTreeSet, never iteration-dependent HashMap output.

Return ADMIT only when every prerequisite passes; otherwise BLOCKED.

Commit admission and evidence-set hash atomically.

Canonical decision hash:

SHA256("CVIR-DECISION-V1" || request_bytes || policy_hash || evidence_set_hash || decision_code || reason_code)

Reason codes must have fixed precedence. Exclude wall-clock timestamps, process IDs, database row IDs and nondeterministic diagnostics.

4. Permutation-invariance replay test

cvir_permutation_restart_1000

For seeds 0..999:

Shuffle the same receipt corpus into a fresh SQLite database.

Include duplicates, contradictions, stale/future ticks, invalid signatures and missing stages.

Restart the Rust process; reopen the database.

Execute identical requests under fixed policy and logical time.

Compare canonical decision bytes, decision hashes and canonical admission records against the reference.

Acceptance criterion: 1,000/1,000 identical outputs, including rejection reasons; zero unauthorized admissions.

Qualification: This guarantees deterministic outputs under the specified assumptions for identical logical receipt sets, provided cryptographic primitives behave deterministically. The test establishes empirical permutation invariance, not a universal formal proof.

References: SQLite transaction semantics (2024–2026); Rust BTreeMap; RFC 8949 canonical CBOR (2020) as an alternative encoding; Wasmtime/Ascent (2024–2026) for deterministic policy execution patterns.

Status: Proposed architecture; no verified published CVIR-specific 1,000-seed result.
