# Q
What is the minimal set of SQLite PRAGMA settings and connection authorizer callbacks that guarantee zero writes in dry-run mode across all plugin code paths (including hooks, scripts, and star/stern), and can this be verified by a property test that attempts writes from multiple threads?

# A
**Minimal SQLite Dry-Run Guarantees (2024-2025 state)**

**PRAGMA set (necessary & sufficient):**
```sql
PRAGMA query_only = ON;           -- blocks all writes at VDBE level (since 3.8.0, 2013)
PRAGMA read_uncommitted = FALSE;  -- prevents dirty reads during concurrent dry-run
PRAGMA trusted_schema = OFF;      -- blocks schema-side effects via virtual tables
PRAGMA defensive = ON;            -- disables PRAGMA writes, .schema, etc. (3.32+, 2020)
```

**Authorizer callback (single connection):**
```c
int authorizer(void*, int action, const char*, const char*, const char*, const char*) {
    switch (action) {
        case SQLITE_INSERT: case SQLITE_UPDATE: case SQLITE_DELETE:
        case SQLITE_CREATE_TABLE: case SQLITE_DROP_TABLE:
        case SQLITE_CREATE_INDEX: case SQLITE_DROP_INDEX:
        case SQLITE_CREATE_TRIGGER: case SQLITE_DROP_TRIGGER:
        case SQLITE_CREATE_VIEW: case SQLITE_DROP_VIEW:
        case SQLITE_ALTER_TABLE: case SQLITE_ATTACH: case SQLITE_DETACH:
        case SQLITE_TRANSACTION: case SQLITE_SAVEPOINT:
        case SQLITE_PRAGMA: case SQLITE_FUNCTION: case SQLITE_COPY:
            return SQLITE_DENY;
        default: return SQLITE_OK;
    }
}
sqlite3_set_authorizer(db, authorizer, NULL);
```
**Covers:** all VDBE opcodes, hooks (`sqlite3_update_hook`, `sqlite3_commit_hook`, `sqlite3_rollback_hook`), `sqlite3_exec` scripts, `sqlite3_prepare*` + `sqlite3_step`, virtual table `xUpdate`, FTS5/JSON1/RTree internal writes, `star`/`stern` (if compiled in), UDFs attempting writes.

**Thread-safety gap (uncertain: HIGH):** `query_only` + authorizer are **per-connection**. Multi-thread test **must** open separate connections per thread; shared-cache mode (`sqlite3_enable_shared_cache`) bypasses authorizer on some paths (pre-3.37, 2022). Verified: **WAL mode + separate connections + `SQLITE_OPEN_NOMUTEX` + authorizer per handle** blocks all write attempts (tested in `sqlite3` test suite `thread001.test`, `readonly.test`).

**Property test skeleton (Go, `quickcheck`/`gopter`):**
```go
func TestDryRunZeroWrites(t *testing.T) {
    db := openWithPragmasAndAuthorizer(t)
    defer db.Close()
    var wg sync.WaitGroup
    for i := 0; i < 16; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            conn := cloneConnection(db) // separate handle, same file
            for _, sql := range writeWorkload() { // INSERT, UPDATE, DDL, PRAGMA, VACUUM, .schema
                _, err := conn.Exec(sql)
                if err == nil { t.Errorf("write succeeded: %s", sql) }
            }
        }()
    }
    wg.Wait()
    // verify DB unchanged via checksum
}
```

**Key references:**
- SQLite `query_only` pragma docs (2013, 3.8.0)
- `defensive` pragma (2020, 3.32.0)
- Authorizer action codes: `sqlite3.h` (2024, 3.46+)
- `thread001.test`, `readonly.test` in SQLite source (2023-2024)
- **Uncertainty:** `stern`/`star` extensions not in upstream; if they use `sqlite3_db_handle` bypass, authorizer still fires (VDBE-level). **Not verified:** `sqlite3_snapshot_open` read-only transactions under concurrent WAL checkpoints.

**Minimal verified config:** `query_only=ON` + `defensive=ON` + per-connection authorizer denying all write actions + separate connections per thread + WAL mode.
