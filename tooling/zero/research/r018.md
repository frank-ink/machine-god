# Q
What is the minimal SQLite WAL + hash-chain schema that provides tamper-evident event ordering for CVIR admission replay while allowing concurrent readers and a single writer actor, and what are the measured p99 latency bounds for append+checkpoint on NVMe vs SSD under mixed read/write load?

# A
SQLite WAL + hash-chain for CVIR replay

Finding: A single-writer SQLite WAL database can provide tamper-evident event ordering, concurrent snapshot readers and deterministic CVIR replay. However, WAL is not itself tamper-evident, and published measurements do not establish universal NVMe-versus-SATA-SSD p99 bounds for combined append and checkpoint latency.

1. Minimal schema
SQL

PRAGMA journal_mode=WAL;
PRAGMA synchronous=FULL;
PRAGMA wal_autocheckpoint=0;

CREATE TABLE events (
  seq INTEGER PRIMARY KEY,
  tick INTEGER NOT NULL CHECK(tick>=0),
  event_id BLOB NOT NULL UNIQUE,
  kind TEXT NOT NULL,
  payload BLOB NOT NULL,
  prev_hash BLOB NOT NULL
    CHECK(length(prev_hash)=32),
  chain_hash BLOB NOT NULL UNIQUE
    CHECK(length(chain_hash)=32)
) STRICT;

CREATE TABLE cvir_decisions (
  request_hash BLOB PRIMARY KEY,
  snapshot_seq INTEGER NOT NULL,
  policy_hash BLOB NOT NULL,
  receipt_set_hash BLOB NOT NULL,
  decision_hash BLOB NOT NULL,
  admitted INTEGER NOT NULL CHECK(admitted IN(0,1))
) STRICT;


Add BEFORE UPDATE/DELETE triggers rejecting changes to both tables. These prevent ordinary SQL modifications, not privileged file tampering.

Persist prev_hash, chain_hash and event atomically. Readers use independent read-only connections.

For tamper evidence against privileged attackers, periodically sign and anchor the chain head externally. Without an external anchor, an attacker can rewrite the entire chain.

CVIR replay: Freeze snapshot_seq; replay events in ascending sequence, then independently sort canonical CVIR receipts for permutation-invariant admission decisions.

Disable automatic checkpointing and schedule explicit PASSIVE checkpoints outside the latency-critical path. SQLite permits concurrent readers and one writer; long-lived readers can prevent checkpoint completion.

Separate checkpoint p99: No sufficiently comparable, verified NVMe-versus-SATA SSD measurement was found. Combining unrelated append and checkpoint percentiles would be statistically invalid.

4. Benchmark required for EntityOS

Measure independently:

append_p99: transaction start → durable commit.

checkpoint_p99: checkpoint invocation → completion.

end_to_end_p99: enqueue → durable acknowledgement.

reader_p99: indexed snapshot lookup.

WAL growth, checkpoint starvation and crash recovery.

Repeat on the same machine with NVMe and SATA SSD, identical databases, transaction sizes, concurrency and synchronous=FULL. Include checkpoint bursts and long-lived readers.

Recommendation: Single Rust writer actor, bounded event queue, WAL/FULL, short-lived readers and externally anchored hash-chain heads.

Principal risk: Checkpoint starvation and storage synchronization stalls can increase tail latency despite low average append times. No credible fixed p99 guarantee follows from storage class alone.
