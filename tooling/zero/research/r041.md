# Q
Which property-based (Hypothesis) invariants and mutation-testing setup can prove that a fail-closed Markdown capability-ledger checker rejects every status-evidence-promotion coupling violation and every broken tracking-issue anchor without false positives on the repository's own documentation?

# A
Fail-closed Markdown capability-ledger checker (2024–2026)

Finding: Hypothesis property-based testing, metamorphic tests and mutation testing can establish strong evidence that a capability-ledger checker rejects unauthorized promotions and broken tracking anchors. They cannot mathematically prove correctness for unrestricted Markdown.

3. Mutation-testing setup

Use mutmut (2024–2026) against the checker itself.

Generate document mutations covering status escalation, evidence deletion, receipt substitution, capability-ID mismatch, issue-number substitution, deleted anchors, duplicate headings, URL encoding and Markdown link syntax.

Use an independent oracle built from typed capability objects, not the checker’s parser.

For GitHub Markdown heading links, reproduce GitHub's slug-generation rules, including duplicate-heading disambiguation. ESLint's no-missing-link-fragments uses github-slugger.
