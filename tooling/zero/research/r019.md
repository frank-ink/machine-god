# Q
What is the minimal set of SQLite PRAGMA settings and Rust connection-pool configuration that guarantees single-writer serializability, zero reader-writer blocking, and crash-safe WAL checkpointing for a 500MB unified.db under 100 concurrent read-only connections, with measured p99 append latency < 1ms on NVMe?

# A
SQLite WAL + Rust: minimum reliable configuration (2024–2026)

Verdict: Single-writer serializability is achievable. Zero reader–writer blocking and guaranteed p99 append latency below 1 ms are not achievable through PRAGMAs alone, particularly with 100 simultaneous readers and crash-durable commits.

SQLite WAL normally allows readers and a writer to operate concurrently, but checkpoints, recovery, lock acquisition and long-lived read transactions introduce exceptions.

+1

1. Minimal PRAGMAs
SQL

-- Set once during initialization:
PRAGMA journal_mode=WAL;

-- Writer connection:
PRAGMA synchronous=FULL;
PRAGMA wal_autocheckpoint=0;
PRAGMA busy_timeout=1000;
PRAGMA foreign_keys=ON;

-- Each read-only connection:
PRAGMA query_only=ON;
PRAGMA busy_timeout=100;

2. Rust connection architecture

Use Tokio + rusqlite, with three separate connection roles.

Role

	

Configuration




Writer

	

Exactly 1 dedicated connection, owned by a writer actor

Checkpointer

	

1 separate maintenance connection

Writer receives requests through bounded tokio::sync::mpsc; serialize transactions with BEGIN IMMEDIATE.

Readers use short-lived snapshot transactions and independent connections, never a shared connection mutex.

Run blocking SQLite operations on dedicated threads or a bounded blocking executor.

Disable shared-cache mode; limit reader transaction duration and enforce timeouts.

Use PRAGMA wal_checkpoint(PASSIVE) periodically; monitor checkpoint progress and WAL size. Schedule RESTART/TRUNCATE only during maintenance windows, since they can wait for readers or writers.

3. Empirical evidence

ALEX — Adaptive Log-Embedded Extent Layer (2026): Linux NVMe experiments reported sub-0.1 ms p99 for its optimized storage layer, while baseline SQLite WAL exhibited millisecond-scale tail spikes. The experiment did not validate 100 concurrent readers or the proposed configuration. 
MDPI

SQLite WAL documentation (2026): Checkpoints can be delayed indefinitely by persistent readers, and WAL still permits SQLITE_BUSY under certain conditions. Therefore, zero blocking is not a documented guarantee.

4. Required acceptance benchmark

For the actual 500 MB unified.db, test 100 readers, continuous event ingestion, checkpoint bursts and crash/restart recovery.

Acceptance criteria:

Exactly one writer and no concurrent write transactions.

No acknowledged transaction lost after simulated crash under the tested durability conditions.

Measured durable append p99 <1 ms, including queueing and commit.

No checkpoint starvation or unbounded WAL growth.

Explicit metrics for SQLITE_BUSY, reader timeouts and checkpoint stalls.

Recommendation: Use WAL/FULL with one writer actor and bounded read-only connections. Treat sub-millisecond p99 as a benchmark target, not a configuration guarantee. If storage fsync tail latency exceeds that target, batching or a different durability architecture is required.
